# 设计说明

本文档说明项目的整体设计、关键技术取舍、开发过程中遇到的问题及解决方式，以及未完成部分的原因。

## 一、整体架构

```text
┌─────────────────────────────────────────────────────────────┐
│                        浏览器（Vue3）                        │
│   记账表单 / 小票上传 / 统计图表 / 自然语言查账输入框          │
└──────────────────────────┬──────────────────────────────────┘
                           │ HTTP / JSON（Vite 代理 /api → 8080）
┌──────────────────────────▼──────────────────────────────────┐
│                    Spring Boot 后端（8080）                  │
│                                                             │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────────────┐  │
│  │ ai/         │  │ bill/       │  │ stat/               │  │
│  │ AiController│  │ BillController│ │ StatsController     │  │
│  │ AiClient    │  │ BillRepository│ │ StatsService        │  │
│  └──────┬──────┘  └──────┬──────┘  └──────────┬──────────┘  │
│         │                │                    │             │
│         │         ┌──────▼────────────────────▼──────┐      │
│         │         │        H2（文件模式）            │      │
│         │         │        ./data/gduf-bill.mv.db    │      │
│         │         └──────────────────────────────────┘      │
└─────────┼───────────────────────────────────────────────────┘
          │ HTTPS（OpenAI 兼容格式）
┌─────────▼──────────┐
│  DeepSeek API      │
│  deepseek-flash    │
│  （文本 + 图片）    │
└────────────────────┘
```

三层结构：

- **Controller 层**：只负责接收参数、做参数校验、返回统一响应结构（`ApiResponse`），不写业务逻辑
- **Service 层**：`StatsService` 承担统计聚合逻辑，`AiClient` 承担与模型通信
- **Repository 层**：继承 `JpaRepository`，通过方法命名和 `@Query` 完成数据访问

## 二、模块划分

| 包 | 职责 | 关键类 |
| --- | --- | --- |
| `ai` | 与模型通信：一句话解析、小票识别、查账意图 | `AiClient`、`AiController`、`BillDraft`、`QuerySpec` |
| `bill` | 账单实体与增删查 | `Bill`、`BillController`、`BillRepository` |
| `stat` | 统计聚合：分类、趋势、日期范围 | `StatsController`、`StatsService`、`StatsRepository` |
| `common` | 统一响应结构 | `ApiResponse` |

## 三、关键设计取舍

### 1. 自然语言查账：让模型返回「查询条件」，而不是「答案」

**问题**：如果直接问模型「上个月吃饭花了多少」，它会根据上下文编一个数字，无法保证和数据库一致。

**做法**：模型只把自然语言翻译成结构化查询条件（`QuerySpec`：时间段、分类、聚合方式），真正的数字由数据库 `SUM` 出来。

**收益**：
- 数字一定来自真实数据，不会「幻觉」
- 查询条件可校验、可调试（能看懂模型解析成了什么）
- 换模型不影响业务逻辑

### 2. 金额用 `BigDecimal`，不用 `double`

`double` 是二进制浮点数，`0.1 + 0.2` 会得到 `0.30000000000000004`。金额计算必须精确，所以实体、统计、聚合全部用 `BigDecimal`，除法时指定 `RoundingMode.HALF_UP` 和两位小数。

### 3. 时间字段用 `String`（`yyyy-MM-dd HH:mm:ss`）

**原因**：
- 前后端交换不需要额外配置日期序列化格式（Jackson 3 对 `LocalDateTime` 的默认格式是 ISO 数组，前端处理麻烦）
- 该格式的字典序等于时间序，可以直接用字符串做范围比较、排序、筛选
- H2 中存为定长 `VARCHAR(19)`，查询性能足够

**代价**：失去数据库层面的日期函数能力，跨时区场景需要额外处理。当前单用户本地场景下可接受。

### 4. API Key 通过环境变量注入，配置里带兜底默认值

`ai.api-key=${AI_API_KEY:}`：
- 本地开发：读取环境变量，真实 Key 不进入仓库
- 评审/CI 环境：没有环境变量时用空字符串兜底，应用仍能启动、单元测试仍能通过
- 只有真正发起模型调用时才需要有效 Key，失败返回 50001

如果写成 `${AI_API_KEY}`（无冒号），评审环境缺少变量会直接启动失败，导致「不可复现」。

### 5. 模型输出必须二次校验

模型输出不可控，因此加了两层约束：

1. **提示词约束**：明确列出九个分类枚举、要求不确定填 `null`、给两个 few-shot 示例
2. **代码兜底**：`AiClient` 里用 `CATEGORIES` 集合校验，模型输出了「出行」「吃饭」这类非枚举值时，统一归为「其他」，防止脏数据入库

同时 `response_format: {"type":"json_object"}` 强制模型只输出 JSON，避免「好的，我来帮你分析」这类自然语言混入。

### 6. 小票识别用多模态模型，不接专用 OCR SDK

DeepSeek `deepseek-flash` 已支持图片输入（`content` 为数组，元素类型 `image_url` + base64 data URL）。做法是把上传图片转 base64 内联发送，模型直接返回结构化 JSON。

**收益**：省掉 OCR SDK 的接入与依赖，一套调用格式同时处理文本和图片。
**代价**：识别精度受模型限制，模糊图片需要用户在表单里手动修正。

### 7. 数据库用 H2 文件模式

- 无需安装数据库服务，评审 clone 后直接能跑
- 文件模式（`jdbc:h2:file:./data/gduf-bill`）保证重启数据不丢
- 用 `spring.jpa.hibernate.ddl-auto=update` 自动建表，首次启动零配置

**未使用 `AUTO_SERVER=TRUE`**：该参数用于多进程同时访问同一 H2 文件，会生成 `.lock.db` 记录内部服务地址。当同一份 `data/` 目录既被 Docker 容器挂载、又在本机直接运行时，该地址指向容器内网（`172.17.0.2`），本机连不上会超时。单进程场景下无需它。

### 8. Docker 采用三阶段构建，前端打包进静态资源

| 阶段 | 内容 | 作用 |
| --- | --- | --- |
| `frontend` | node:20-alpine + pnpm | 构建 Vue，产出 `dist/` |
| `backend` | maven + temurin-25 | 把 `dist/` 复制进 `src/main/resources/static`，打成 jar |
| 运行 | temurin-25-jre | 只含 JRE + jar，镜像小 |

**收益**：评审一条 `docker run` 就能同时得到前端页面和后端接口，不需要分别启动两个服务，也不需要安装 Node。

前端在国内网络下构建慢，Dockerfile 里把 pnpm registry 指向 npmmirror 镜像，并补齐 `pnpm-workspace.yaml` 的复制，否则 `pnpm install` 会超时。

## 四、遇到的问题与解决方式

### 1. Spring Boot 4 使用 Jackson 3，包名迁移

**现象**：`import com.fasterxml.jackson.databind.ObjectMapper` 编译报「程序包不存在」。

**原因**：Spring Boot 4.1.2 依赖 Jackson 3（`tools.jackson:jackson-databind:3.1.7`），包名从 `com.fasterxml.jackson` 改为 `tools.jackson`。

**解决**：改用 `tools.jackson.databind.json.JsonMapper`，通过 `JsonMapper.builder().build()` 创建实例（Jackson 3 推荐方式，`new ObjectMapper()` 已不推荐）。

### 2. `RestClient` 拼接 baseUrl 与 uri 时路径被截断

**现象**：`baseUrl = https://api.deepseek.com/v1` + `uri = "/chat/completions"`，实际请求变成 `https://api.deepseek.com/chat/completions`，404。

**原因**：URI 解析规则中，以 `/` 开头的路径是「从根开始」，会替换掉 baseUrl 的路径部分。

**解决**：baseUrl 只写域名 `https://api.deepseek.com`，完整路径写进 uri：`/v1/chat/completions`。

### 3. Windows PowerShell 输出中文乱码

**现象**：接口返回的中文在终端显示为 `äº¤é`。

**原因**：PowerShell 5.1 默认按 ISO-8859-1 / 系统 ANSI 解码响应体，而服务端返回 UTF-8。

**解决**：测试时显式设置 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`，并手动用 `UTF8.GetString(RawContentStream)` 解码。根本方案是改用 Postman 或现代终端。

### 4. PowerShell 脚本中文编码导致解析失败

**现象**：`.ps1` 脚本里含中文，执行报「字符串缺少终止符」。

**原因**：脚本以 UTF-8 保存，但 PowerShell 5.1 默认按 ANSI 读取，中文字节被错误拆分。

**解决**：脚本中只使用 ASCII 字符，中文数据放在 CSV 文件里，通过 `Import-Csv -Encoding UTF8` 显式指定编码读取。

### 5. Docker 容器与本地同时运行导致数据库连接超时

**现象**：本地启动报 `SocketTimeoutException: Connect timed out: 172.17.0.2:45495`。

**原因**：容器内 H2 启用 `AUTO_SERVER`，把内部服务地址写入 `.lock.db`；该文件经卷挂载留在宿主机，本机启动时读取并尝试连接容器内网地址。

**解决**：移除 `AUTO_SERVER=TRUE`（单进程场景不需要），删除残留 `.lock.db`，并规定本地开发与容器演示不同时运行。

### 6. 实体类文件名大小写不一致

**现象**：`bill.java` 中声明 `public class Bill`，编译报「类 Bill 应声明在 Bill.java 中」。

**原因**：Java 要求 public 类名与文件名完全一致（大小写敏感），Windows 文件系统不区分大小写掩盖了问题。

**解决**：用 `git mv` 分两步重命名（`bill.java → Bill.tmp → Bill.java`），否则 Git 在大小写不敏感的 Windows 上识别不到改名。

### 7. 接口文档出现重复章节

**现象**：`docs/接口文档.md` 中「按日期范围统计」出现两份。

**原因**：统计模块开发时已向文档补充过该接口，后续又按新人视角补了一份，未先核对现文。

**解决**：保留位置正确的一份，删除重复章节，并在团队内约定「改接口文档前先 pull 并全文搜索接口路径」。

## 七、团队协作

- 以一个 `main` 为主线，各模块按包划分归属，减少冲突
- commit message 采用 `type: 说明` 格式（`feat` / `fix` / `docs` / `chore` / `refactor`）
- 接口契约先行：先定 `docs/接口文档.md`，前后端按文档并行开发
- 提交前自查：无 `target/`、`.idea/`、`data/`、API Key 泄露
